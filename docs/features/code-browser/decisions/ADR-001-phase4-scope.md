# ADR-001：代码浏览器阶段④——暂不引入 Java LSP，先做受控补丁编辑（受限边界）

## 状态

已接受（评估决策，待实现验证）

## 决策

代码浏览器阶段④采纳以下两条：

1. **暂不引入 Java Language Server（Eclipse JDT-LS / jdtls / java-language-server）。**
2. **实现受控补丁编辑（AI 生成 → 用户审视 → 用户明确应用 → 一次性写入），不内置编辑模式、不常驻索引。**

理由与边界如下。

## 背景

- ROADMAP §V2 代码浏览器把阶段④描述为「用户明确进入编辑模式，AI 生成补丁或差异；在确有需要时再评估 Java Language Server，不自动提交或推送」。
- 阶段①（v0.1.8）交付了本地项目只读查看 + 轻量符号跳转（接口→实现、JavaBean 类型→类定义），靠按需扫描的项目内符号索引。
- 阶段③（v0.1.9 + v0.1.10）交付了收藏文件、代码书签、发送到 AI（确认面板 + 对话预填）、转为 Todo、终端定位——已建立「代码 → AI → 工作台/终端」的协作闭环。
- 至此，Elwright 的代码上下文入口走完了「只读 + 轻量语义跳转 + 联动工作台」三阶段；阶段④需要回答「要不要写代码」。

## 评估过程

### Java Language Server 选项

| 维度 | Eclipse JDT-LS（jdtls） | 不引入 |
|---|---|---|
| 能力 | 完整 Java 语义：定义、引用、重命名、签名补全、类型推断、调试支持 | Elwright 阶段①②已覆盖 80% 高频场景（项目符号索引） |
| 启动 | JVM 启动 1–3 秒，驻留内存 200–600 MB | 0 额外常驻进程 |
| 打包 | jar + 运行时（Java 11+ 已是 Java 项目前提，但首次启动用户需感知 jdtls） | — |
| 跨平台 | macOS / Linux / Windows 全支持但启动需 JDK | — |
| 用户预期 | 「编辑器」暗示用户期待开箱即用的语义跳转 | 当前阶段已满足 |
| 维护成本 | 与上游保持版本同步，签名校验、Java 版本兼容 | 0 |

jdtls 能补齐的能力主要是「跨文件引用」「重命名」「类型推断补全」——这些是 IDE 工具的强项，但不是 Elwright 主张的「代码上下文入口」核心。Elwright 不是编辑器，受众已经能用 IDE 解决这些问题。

### 受控补丁编辑

阶段③的「发送到 AI」流程已建立：选中 → 确认面板 → 填入 AI 对话 → 用户发送 → 模型回复。扩展到「AI 回复里夹带代码补丁 → 用户在 Elwright 中预览 → 一键应用」是顺水推舟，不引入新的范式。

候选路径：
- 完整 IDE（monaco/codemirror with vim / 多光标 / 撤销栈）—— 工作量大、与阶段①②③的「只读 + 联动」定位不符。
- 轻量补丁面板（diff 视图 + 接受/拒绝单文件粒度）—— 与现有「确认面板」同源，不引入新交互范式。

## 决定

### 1. 暂不引入 Java Language Server

- 拒绝 jdtls 类常驻进程；架构方案 §11「不常驻启动高内存后台索引服务」的红线继续适用。
- 现有按需扫描符号索引已能满足「查看与定位」需求；多文件引用、类型推断补全、重命名等 IDE 强项不在 Elwright 范围内。
- 如果未来用户场景证明引用追踪是日常刚需，再立阶段⑤专项评估——届时也不一定要 LSP，可以是基于 ripgrep + ctags 的轻量增强。

### 2. 实现受控补丁编辑

最小可用形态（定义与边界，下一阶段实施时再细化）：

- **触发**：用户在 AI 对话回复中点击「应用到代码」按钮（阶段③已把代码片段送到对话；阶段④新增补丁识别与预览入口）。
- **识别**：模型回复带统一 diff / unified diff 块（` ```diff `），Elwright 解析后只展示「文件路径 + 行范围 + 增删行」三栏预览。
- **应用**：用户在预览面板里逐块「接受 / 拒绝」，单文件粒度；接受后才写入项目源文件。
- **写入约束**：
  - 写入前要求「用户项目目录」必须是显式打开的项目；敏感文件（`.env`、私钥、证书、`/etc/`、`*/node_modules/`、`*/target/`）一律拒绝。
  - 不自动保存，写入后保留改动但不创建 git commit / 不推送。
  - 应用记录写入用户配置层（`code-browser.json` 新增 `appliedPatches`，记文件 + 时间 + commit 哈希或撤销前内容快照，便于用户撤销）。
- **撤销**：用户在面板可一键恢复到补丁应用前的内容（基于快照，不依赖 git）。
- **失败兜底**：写入冲突（文件已被外部改动）→ 拒绝应用并提示用户先刷新文件预览，再决定合并或放弃。
- **不进入**：行内编辑模式、自动保存、内置多光标、内置撤销栈（按 IDE 体感对待）、与 git 客户端集成。

## 影响的范围

- 受影响组件：`CodeBrowserView` / `CodeTabs` / `CodeContextActions` 新增「应用到代码」按钮；`ChatView` 在助手消息块里识别 diff 并渲染预览面板；core 新增 `apply_patch` 命令（IPC）。
- 不受影响：阶段①②③（只读 / 轻量跳转 / 联动工作台）继续作为代码浏览器主线。
- 不受影响：AI 对话阶段⑤（待排期），本 ADR 不约束对话后续方向。

## 拒绝的方案

- **常驻 jdtls / 任何语言服务**：违反「不常驻高内存后台索引服务」红线；与 Elwright 不是编辑器的定位冲突。
- **内置编辑器模式（monaco/codemirror 多光标）**：与本阶段能力边界不符；用户有 IDE 可用。
- **自动保存 + 自动 commit / 推送**：违反 ROADMAP「不自动提交或推送」；违反 ADR-001「能力调用必须显式确认」原则。
- **AI 直接写文件**：违反 AI 对话能力调用必须用户确认的边界。

## 验证

实施后回填：

- 补丁识别单元测试：合法 diff / 缺行号 / 多文件 / 含二进制补丁 四类。
- 应用流程端到端：选中 → 确认 → 写入 → 用户撤销 → 文件恢复原状。
- 敏感文件拒绝：`.env`、私钥、`/etc/`、构建产物目录各一例。
- 写入冲突兜底：先在 Elwright 之外修改文件，再回到 Elwright 应用补丁——拒绝并提示。
- 本地五道闸：cargo 全部 / 严格 clippy / fmt / vitest（含 chatProposal 增项） / build。
- 真机点验：选中片段 → AI 回复 → 应用补丁 → 撤销；写入冲突与敏感文件拒绝各一例。
