## v2 修订（Codex `>` 坐标对齐）

Codex `>` 几何特征（对齐目标）：尖端是锐利单点、两臂等粗、内凹自然、无外凹缺口。未能从 thesvg.org / openai/codex 仓库抓到 Codex 官方 SVG（站点 JS 渲染、仓库无品牌图标文件），改为从用户参考图本身提取 `>` 比例（参考图即用户手绘的 Codex `>`），并修正执行：

- 移除尖端外凹缺口 → 改为锐利单点 `L700 484 L736 512 L700 540`
- 移除右侧碎星点 → 单一符号，干净
- 两臂等粗（左立面各 96px）、内凹顶点 `L572 512` 自然
- 整体笔画收窄到 100，E 比例更稳

## v4 验证（单字母 E + 中横协调地变成 >）

用户要求在 v3 单字母 E 基础上把中横协调地变成 `>`（非直接替换）。重读参考图（144px 高分辨率重解析，纠正了首轮下臂走向的误读）：参考图确为「上横杠 + 中间 `>` 折角 + 下横杠」，`>` 两臂在右侧汇成锐尖角、带细内凹缝（缝宽约 1% 画面）。

协调手法：`>` 两臂粗 104（= 横杠粗）、左端连立柱、尖端锐利、内凹缝压到 12px（与参考图 ~1% 缝宽一致）。

48px 像素图：`>` 尖端锐利、两臂等粗、连立柱；内凹缝在 48px 下被抗锯齿放大显示为 2-3 像素（实际 12px/1024=1.2%，128px dock 尺寸下为细缝）。20px 下 `>` 仍可辨。128px 采样：`>` 尖端白色 `#e0e0e0`、横杠石墨、底黑。全套平台图标已从 v4 重新生成。

设计权衡记录：`>` 的内凹缝是其字符特征（参考图亦有），无法既无缝又读作 `>`；选择与参考图一致的细缝，小尺寸下近似实心横杠（协调），大尺寸下露出 `>` 分缝。

## v5 验证（Σ 形：上横线 + 双斜折 + 下横线）

用户回到参考图原貌，要求按参考图结构做：上下两条横线都是水平直线、中间 2 个平行四边形块要与上下线左侧对齐、块与线之间留缝。

测量参考图（1206×956 JPG，缩放 144×114 ASCII 解析）：

- 上横线 y=28-32，x=29-120（水平）
- 下横线 y=86-91，x=25-125（水平）
- 上斜块 y=36-60：**左对齐起点 x=16，右下倾**（左上 y=36、右上 y=60）—— 即**左高右低**
- 下斜块 y=63-85：**反向**（左上 y=85、右上 y=63）—— 即**左低右高**

两个块在右端汇成 V 折角。

设计实现（1024×1024 视口）：

- 上横线：`x=264..760, y=296..368`，粗 72，圆角 rx=16
- 上斜块：左对齐 x=264，左沿 (264,408)→(264,480)，右沿 (760,449)→(760,521)，左高右低，斜率 0.083
- 下斜块：左对齐 x=264，左沿 (760,503)→(760,575)，右沿 (264,544)→(264,616)，反向倾斜（左低右高）
- 下横线：`x=264..760, y=656..728`，粗 72，圆角 rx=16
- 中缝在折点处自然收口（两块重叠约 18px → 视觉上无中缝，但左端 64px 中缝清晰）
- 上下缝宽 40-48（约 4-5% 画面）

32/48/64/128px 多尺寸 ASCII 验证：Σ 形识别清晰；上横线圆角呈现；中缝左端可见；折角处形成 V 汇聚；下斜块反向倾斜明显；下横线水平无上翘。

彩色版：上下横线白色 `#f5f5f5`，Σ 腹部青渐变 `#2fb8a6→#0e7f8c`，采样点 (24,28) RGB(17,27,27) 偏青绿——渐变生效。

`tauri icon` 从 1024 png 重新生成全平台图标集（icns/ico/32/64/128/512 + iOS AppIcon 全尺寸 + Android mipmap 全套），32px 下 Σ 形仍可辨。

设计权衡：折角处两块重叠 18px 是 Σ 字的标准形态（参考图也如此），不是贴合错误；左端中缝 64px 保持缝宽"留缝隙不要完全贴合"的语义。
