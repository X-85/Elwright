# 接口文档格式化 · 离线 SOP

> 这是技能型能力 `api-doc-formatter` 的离线降级文档。配置了 LLM 时由 AI 自动转换；离线时按本文手动执行。
> 注：该能力归类型待确认（脚本/技能）——若日后转为脚本型，本文转为脚本的使用说明。

## 用途

把五花八门的原始接口说明（Word/聊天记录/代码注释里的片段）整理成统一格式的接口文档，团队任何人拿到就能对接。

## 标准格式模板

```markdown
## <接口中文名>

- **接口 ID**：<唯一标识>
- **方法与路径**：`POST /api/v1/orders`
- **用途**：一句话说明做什么。
- **调用方**：谁在用（系统/模块）。

### 请求参数

| 参数名 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| orderNo | string | 是 | 订单号，32 位内 | SO20260821001 |

### 响应字段

| 字段名 | 类型 | 说明 | 示例 |
|---|---|---|---|---|
| code | int | 0=成功 | 0 |

### 错误码

| 错误码 | 含义 | 处理建议 |
|---|---|---|
| 4001 | 订单不存在 | 检查 orderNo |

### 请求示例

```bash
curl -X POST 'http://<host>/api/v1/orders' -d '{"orderNo":"SO001"}'
```
```

## 使用方法（离线）

1. **抓要素**：从原始材料里先抓「方法+路径」和「用途」，定下接口名。
2. **填表**：把散落的参数描述逐个填入请求/响应表格；类型不明的标 `unknown` 并向接口负责人确认，不要猜。
3. **补示例**：从日志或联调记录里找一条真实请求做成 curl 示例。
4. **补错误码**：没有错误码说明的，向开发要，缺失即文档债，登记待补。
5. **过一遍**：让一个没接触过该接口的同事只看文档发起一次调用，卡在哪补哪。

## 边界情况

- 原始材料互相矛盾时：以代码实际实现为准，并在文档中标注差异来源。
- 批量转换大量接口：先做一份模板样例对齐格式，再逐个套用。
